# ADR-0017: Expression size limits (resolves SPEC-Q-002)

**Status:** Accepted (2026-10-12)

## Context

Spec 1.0.0 sets no limit on statement size. The fuzz stress inputs (a 20,001-term
sum, 2,000 nested parentheses) and the robustness probes (10,000- and
100,000-term `AND`/`OR` chains) produced every possible outcome. Some engines
computed the result. Others answered `PARSE_ERROR` or `RESOURCE_LIMIT`. Go, Java
and Clojure never answered although `timeout_ms` was set, and both assembly
engines crashed (SIGSEGV) when parallel or vectorized workers recursed over long
chains. Where the spec is silent behaviour is implementation-defined, so none of
this could be judged.

## Decision

1. Change request CR-6 (`spec/changes/expression-limits.md`, capability
   `change.expression_limits`, spec version 1.3.0-cr6) settles the question:
   * **Minimums every engine executes in every mode:** 1 MiB of text, nesting
     depth 1,000, and 25,000 operands. A chain of one binary operator counts as
     one level of nesting, so long `OR`/`AND`/`+` chains are covered by the
     operand minimum, not the depth minimum.
   * **Beyond an engine's own limits:** `RESOURCE_LIMIT`, naming the measure.
     It MAY take precedence over `PARSE_ERROR`, because the check may stop
     parsing early.
   * **The timeout covers parsing, binding and planning** as well as
     execution. `TIMEOUT` is sent within 1 s of expiry in every stage; the
     100 ms rule for operators is unchanged.
   * **Stack exhaustion in any thread must not end the process.**
2. It is a capability-scoped change like CR-1 and CR-2, not a base-spec patch.
   * Engines report `spec_version` "1.0.0", and the Phase 1 conformance suite
     checks that string, so bumping the base version would fail every engine.
   * Engines built against 1.0.0 were entitled to any behaviour here.
   * Any future engine task that touches expression handling (for example
     fixing the probe defects) includes the capability.
3. The minimum values follow from use, not from the current engines. Generated
   SQL (key lists, `OR` of conditions, wide `CASE` mappings) reaches thousands
   of terms. 1,000 levels is the depth limit SQLite uses by default. 1 MiB
   comfortably holds 10,000-term statements (about 120 KB).
4. The check is the black-box probe `expression_limits` in
   `tests/regression/robustness_probe.py`, not `.pqt` conformance files, since
   its statements are generated and up to 1.3 MB long. It runs on every engine.
   For engines that do not claim the capability the result is reported as
   informational.

## Consequences

* All eight current engines are measured against CR-6 for information
  (`results/correctness/robustness/<engine>.json`, probe `expression_limits`).
  None claims the capability, so no conformance result changes.
* Permanent adoption into the base spec waits for a base release that also
  updates the `spec_version` conformance case.
